The heap comes from the request

AI prototypes often arrive overbuilt: ask for an app, receive ten screens, spend the afternoon deleting eight. This page shows where that comes from. The same model, asked for the same app, built a whole product when the request had no scope and a single task when it did. With the scope set, it built three approaches in less time than the one overbuilt version, and one prototype that switches between three fidelities.

Every prototype here is unedited AI output, generated October 5 and 6, 2026. Prompts, counts, and the scripts that produced them are in the repository.

Same app, two requests

Unscoped request

Build a clickable prototype of a mobile web app that lets residents report potholes to their city.

11 screens · 212 s

Nobody asked for a welcome flow, a report history, status updates, or a profile. With no scope and an instruction to make its own decisions, the model filled in a whole product.

Scoped request

Build a clickable prototype of a mobile web app that lets residents report potholes to their city.

Scope: one task only. A resident reports a single pothole: marks its location, optionally adds a photo, and receives a confirmation. Three screens maximum. Out of scope: accounts or sign-in, report history, status tracking, notifications, settings, onboarding, and any other feature.

Render it as a hand-drawn grayscale wireframe with placeholder text, no color or imagery.

3 screens · 37 s

The highlighted paragraph is the whole difference in scope. It is drawn as a sketch because the request asked for one; the same scope polished is further down.

Both requests ended with the same technical block, which included "Do not ask questions; make your own decisions." Apart from the scoped request's rendering line, scope was the only difference.

The speed, spent on alternatives

The same scoped request, with one added line naming a starting point, produced three distinct approaches in 144 seconds combined, less than the single unscoped build took. Seeing a design among alternatives draws more candid criticism than seeing it alone, and at this cost there is little reason to show participants only one.

Fidelity is a setting

This prototype came from one scoped request that asked for three fidelities in a single build. Use the control at its top to switch between them. All three share one set of screens and one set of words, so a change made to the prototype appears in every fidelity at once.

Fidelity: build the prototype once, with a control that switches the whole prototype between three fidelities. Switching must not change the screens, the flow, or any wording; every fidelity uses the same real copy.
1. Sketch: hand-drawn look, wobbly lines, handwriting-style font, grayscale.
2. Wireframe: crisp gray boxes, system font, consistent grid, one accent color marking what can be tapped.
3. Polished: finished visual design with color, typography, and icons.

Added to the same scope paragraph as above. Full prompt in the repository.

  • SketchEarly sessions, while the concept itself is in question. The roughness invites people to argue with the idea.
  • WireframeTask testing once the flow settles. Real wording in plain boxes, with what can be tapped marked.
  • PolishedLate sessions and the stakeholder readout, where visual hierarchy and buy-in are the questions.

That progression follows a rapid iterative testing study, where a team fixes what breaks between participants and raises fidelity as the design stabilizes. Rebuilding used to set the pace of those fixes. Here, moving between fidelities is a click, and a fix lands in all three.

When the wording is loose

Fidelity changes cleanly only when the request says what must stay. Asked to redraw the unscoped prototype as a sketch "with placeholder text," the model kept every screen and 4 percent of the words. The questions on the details screen, how big the pothole is, where it sits, and whether it is a hazard, became Label A, Label B, and Label C. Asked for the same style while keeping every label and line of copy, it kept all of it. Building fidelity as a view of one prototype, as above, avoids the problem entirely.

Limits

This is one flow, one model, and one run per request; another run could return a different screen count or keep more or less copy. The demonstration shows that the scope in a request set the size of the build and that fidelity can be set by request. It does not show what participants would say about any version.

It also cannot show the half of the skill that matters most. The scope above is a reasonable assumption about what a pothole report needs, not the product of field research. In real work, that paragraph comes from knowing the people, the task, and the organization, and a scope is only as good as the understanding behind it.
